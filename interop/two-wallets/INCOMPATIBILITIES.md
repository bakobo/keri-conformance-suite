# M1 incompatibilities and runtime seams

The KERI 1.x holder inception fetched from a witness parsed and established key state with heti's KERI 2.0 keripy fork. The seams encountered while reaching that result follow.

1. **Writable KERI configuration files.** `interop/two-wallets/compose.yaml:12,24` mounts the witness directory and KERIA config read/write. With read-only mounts, `Configer` fell back to an empty configuration: `Configer(...).get()` printed `{}`, Veridian's `IdentifierService.getAvailableWitnesses()` raised `Misconfigured KERIA agent for this wallet type`, and KERIA logged `no http endpoint` for all six witnesses. The pinned KERIA `src/keria/app/agenting.py:301-305` opens `Configer` and the pinned keripy `Configer` uses `r+b`; Veridian's own compose also uses writable mounts. **Owner:** this harness's Compose configuration.

2. **Node test shim differs from a usable stream global.** Veridian `src/setupTests.ts:9-17` takes `ReadableStream` from `node:util` and assigns an object with an empty prototype. On Node 24, copying that literally caused `TypeError: ReadableStream is not a constructor` during `bootAndConnect`. `interop/two-wallets/veridian-driver/src/m1.ts:3-14` uses `node:stream/web` for the real constructor. **Owner:** this headless driver.

3. **Poller shutdown is a process boundary.** Veridian `src/core/agent/services/keriaNotificationService.ts:169-312,1090-1112` has `while (true)` loops; `stopPolling()` only sets `loggedIn = false`. The driver calls `stopPolling()` and unreferences only the poller timers, so its short-lived CLI exits naturally after writing output. **Owner:** Veridian core's poller lifecycle.

4. **The heti fork's `Baser` is not a context manager.** `with Baser(...)` in the first `fetch_kel.py` run raised `TypeError: 'keri.db.basing.Baser' object does not support the context manager protocol`. `interop/two-wallets/py/fetch_kel.py:24-36` now calls `close(clear=True)` in `finally`. **Owner:** this harness's Python integration.

5. **The pinned Signify package needs its prepare build.** `npm ci --ignore-scripts` left `node_modules/signify-ts/dist` absent, so the driver could not use the package entrypoint. A full `npm ci` in the separate Veridian worktree built it. **Owner:** this harness's installation instructions.

6. **Veridian declares a Node 20 engine.** The pinned `package.json:6` declares `20.x`, while this harness runs on Node 24. `npm ci` emitted `EBADENGINE`; the headless M1 run completed on Node 24 after the stream shim above. **Owner:** this harness's supported runtime choice.

## M2

7. **SEDI SAM schema is a KERI 2.0 shape.** The source at heti `tests/fixtures/sedi/sam-core.schema.json` requires top-level `v,d,i,rd,s,a,e,r` and defines `v,t,d,u,i,rd,s,a,e,r`. For the 1.x ACDC in `schemas/sedi-core-1x.schema.json`, `v` and `d` remain unchanged, `u` remains optional, `i` remains required, top-level `rd` becomes required `ri` with the same registry-SAID definition, `s` and `a` remain required, `e` and `r` keep their original definitions but become optional, and `t` is removed. The nested `a` section is structurally unchanged, including its optional nested `rd`, every required field, and all `{d,u,value}` blocks. heti's keripy `Schemer` computed and verified `$id` `EP3O5QNAho8Z7B9TTTdHWK7Ge_sPgZciw8Y4tYjpITqY`. **Owner:** SEDI schema publication / heti fixtures.

8. **The pinned Signify issuance helper inserts a forbidden attribute timestamp.** `signify-ts/src/keri/app/credentialing.ts:350-355` always adds `a.dt` and saidifies the attribute section, then the ACDC. It does not saidify nested blocks. The first live `credentials().issue` request returned KERIA HTTP 400: `Additional properties are not allowed ('dt' was unexpected)` because the unchanged SAM `a` has `additionalProperties: false`. `veridian-driver/src/issuer.ts:issueSam` uses Signify's `Saider`, `interact`, and keeper signing primitives to submit the same issuance events with a TEL timestamp and no `a.dt`; nested block SAIDs and `u` salts are made client-side. **Owner:** Signify issuance API / SEDI 1.x schema integration.

9. **IPEX delivery needs both agent OOBIs before the grant.** The first grant submitted by KERIA completed as an exchange operation, but the holder had zero KERIA notifications after two minutes. `veridian-driver/src/issuer.ts` now authorizes its `agent` end role, resolves the holder's agent OOBI as well as its witness OOBI, and waits for the holder to connect to the issuer's agent OOBI before submitting the grant. The next clean run delivered `/exn/ipex/grant`. **Owner:** this harness's issuance ordering and OOBI setup.

10. **Veridian treats optional SAM edge definitions as mandatory child schemas.** `veridian-wallet/src/core/agent/services/ipexCommunicationService.ts:1298-1339` recursively resolves every definition in `schema.properties.e`, even when the credential has no `e`. SAM's optional `utahAgent` has no constant `s`, and `guardians` is a group edge, so this path cannot resolve them. The M2 driver limits its runtime resolver bridge to this exact schema SAID and still calls Veridian's `connections.resolveOobi` and `schemas().get`; Veridian's code is untouched. **Owner:** Veridian core schema resolution.

11. **Veridian assumes every admitted credential has `a.dt`.** With the valid SAM attributes, the grant reached `admitAcdcFromGrant`, then `saveAcdcMetadataRecord` at `ipexCommunicationService.ts:454-478` raised `RangeError: Invalid time value` when it parsed undefined `a.dt`. The M2 driver supplies the credential's SAM `issuedDate.value` only to the local metadata save method; the ACDC and CESR bytes are untouched. **Owner:** Veridian core credential metadata.

12. **Schema OOBIs use Veridian's resolver service rather than its contact creator.** `connectionService.ts:137-205` treats `connectByOobiUrl` as a contact operation requiring a shared holder identifier. `connectionService.ts:772-815` exposes `resolveOobi` for the schema URL, and `ipexCommunicationService.ts:1298` uses that service itself. The driver connects to the issuer with `connectByOobiUrl` and resolves the schema with `resolveOobi`. **Owner:** Veridian core service API / this harness's call site.

## M3

13. **Veridian's IPEX history path requires an indexer schema URL.** On the first clean M3 run, the apply reached the holder's KERIA agent, but its notification poller failed repeatedly with `TypeError: Cannot read properties of undefined (reading 'split')` in `IpexCommunicationService.getSchemaUrl` (`veridian-wallet/src/core/agent/services/ipexCommunicationService.ts:1277-1296`). `createLinkedIpexMessageRecord` at lines 558-565 queried `/indexer/<verifier AID>` even though the schema was already resolved from `http://127.0.0.1:7723/oobi/<schema SAID>` and this verifier had no indexer. The operation poller then encountered the same lookup while recording the holder's offer. The local bridge in `veridian-driver/src/m3.ts` supplies that base only while processing messages involving this verifier and schema `EP3O5QNAho8Z7B9TTTdHWK7Ge_sPgZciw8Y4tYjpITqY`; the final clean run reached offer, grant, and admit without Veridian poller errors. Veridian's source and all signed exchanges remain unchanged. **Owner:** Veridian core schema discovery / this harness's schema service.

14. **After migration the holder AID's endpoint still names Veridian's agent, so replies to heti go to Veridian.** heti's grant (`out/heti-grant.cesr`, built by the keripy fork's `ipexGrantExn`, recipient in `a.i`, `rp` empty) was POSTed unchanged by `py/heti_holder.py` to the verifier's agent at `http://127.0.0.1:3902/` with `Content-Type: application/cesr+json`, `CESR-ATTACHMENT` and `CESR-DESTINATION`; KERIA answered 204, notified the verifier, and the verifier admitted it as its first sight of the credential. KERIA then held the presented credential with `iss` status (`out/m3-heti.json`). So the recipient placement did not block delivery. The verifier's admit, however, is logged as `exn event for route /ipex/admit failed behavior verfication` (`out/admit-behavior.log`). The holder AID's only `agent` end role (`out/holder-agent-role.txt`, from `GET /oobi/<holder>/agent`) is Veridian's KERIA agent (`out/m1.json` `keriaAgentPre`), so the admit was routed there, and that agent never saw heti's grant: keripy 2a94929 `src/keri/vc/protocoling.py:79-88` (the copy KERIA bca7acc pins) refuses an admit whose prior message it cannot clone. heti carries no transport and publishes no endpoint of its own (`this.i` @8ht325vx), so after migration it can present but cannot receive the verifier's admit receipt, and Veridian's agent keeps receiving traffic for an AID whose keys heti now also holds. A complete migration needs the new wallet to publish its own end role for the AID (a signed `/end/role/add` reply), and the old wallet to be retired, ideally by a rotation the new wallet performs. `scripts/m3.sh` checks that this observation still holds. **Owner:** heti (no endpoint publication, no rotation of an adopted AID) and the migration flow; not KERIA, not the grant's form.

## M4

15. **A migration export needs the old KERIA agent online for credential evidence.** `veridian-driver/src/export.ts` obtains the mnemonic with Veridian's `Agent.getMnemonic()`, derives the bran through the inverse used by `Agent.recoverKeriaAgent`, and reads `sxlt` from Veridian's local `IdentifierMetadataRecord`. The full 1.x credential stream comes from the holder agent through `credentials().get(said, true)` while it is online; Veridian's local metadata does not contain the full signed issuer KEL, registry TEL, and ACDC stream. `out/export.json` records both sources. **Owner:** Veridian/KERIA wallet export interface.

16. **The headless driver's fake storage is process-local.** M2's `IonicSession` uses `fake-indexeddb`, and `secure-storage-shim.ts` holds key/value pairs in a Map. A later `veridian m3` or `veridian export` process would otherwise lose Veridian's local identifier metadata and bran. `veridian-driver/src/state.ts` snapshots the raw local session and secure-storage values to `out/veridian-state.json` at the end of M2, restores them before `bootAndConnect` in both later commands, and the final clean run reopened the same holder AID without reissuing. This is a headless-driver persistence seam, not a wallet protocol requirement. **Owner:** this harness's storage shims.

17. **The schema-serving issuer helper must end before M3 reuses its port.** The first split-process run reached M2, then `veridian m3` raised `EADDRINUSE` on `127.0.0.1:7723`: terminating only the issuer launcher's parent left its bundle serving the schema briefly. `veridian-driver/src/m2.ts` now starts that helper in its own process group, signals the group and waits for its exit; the next clean M2-to-M3 transition succeeded. **Owner:** this harness's process lifecycle.
