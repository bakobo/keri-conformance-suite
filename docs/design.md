# Design

This document is the reference for how the suite works and why. It is written to stand on its own: the repository's `this.i` records the same decisions while the suite incubates at Bakobo, but `this.i` will be removed when the suite moves to the KERI Foundation, and this file will remain.

The adapter wire protocol has its own document, [`adapter-protocol.md`](adapter-protocol.md). Terms with a meaning specific to the suite are defined at the end of this document, under Terms.

This document describes the suite as designed, and says where something is not built yet. As of October 2026 the runner, the case schema, `kcs check-adapter`, the CESR and KERI cases with their generators, the first batch of ACDC cases with theirs, three adapters, and CI levels 1 and 2 exist. The IPEX layer is designed below and not yet built, and CI level 3 is not built.

## What the suite is for

Implementations of CESR, KERI, ACDC and IPEX need a way to show that they are correct, and today they have none beyond agreeing with keripy on whatever inputs their authors thought to try. A survey of ten Rust codebases in September 2026 found defects that a shared corpus would have caught immediately — for example, CESR counters that count items where the CESR specification requires them to count quadlets, which made every stream unreadable to keripy and every keripy stream unreadable to them.

The suite supplies that corpus. Each **case** is a fixed input together with a set of **assertions** about what an implementation must report for it. An implementation runs the cases through a small **adapter** and the **runner** checks each assertion against what the adapter reports. The result is a **conformance report**: a version-stamped, machine-readable account of which assertions held, which failed, and which did not apply.

## Principles

These rules shape everything below. Each exists to prevent a specific failure.

**The spec text is the authority, not keripy.** Expected values are derived from the pinned specification wherever a generator can do so: the CESR generator reads its code tables from the specification text and encodes from them. keripy, the reference implementation, is used to generate bytes only where the specification gives no tables to derive them from, and to cross-check what the generators produce, never as the authority. Even so, it would be easy for keripy's bugs to become the suite's law. So every assertion cites the spec clause it tests, and where keripy's output contradicts that clause, the case is marked `disputed` instead of being resolved here. A disputed case is excluded from conformance results until the question is settled by the spec working group.

**When the specification disagrees with itself, the keyword sentence governs.** A sentence that carries an RFC 2119 keyword (MUST, SHOULD, MAY) outranks a table, a legend or an example that says something different. The assertion keeps that sentence's level and stays active, and the conflict is recorded in the assertion's `spec_conflicts` and raised with the working group. A case is disputed only when an implementation's behaviour, not the specification's own text, contradicts the clause. For example, the CESR specification says a count code's size MUST count quadlets, while its symbol legends describe the same digits as counting primitives; the cases follow the MUST and record the legends.

**An obligation the specification states only for producers is graded SHOULD for validators.** The CESR specification says, for example, that pad bits MUST be zero, but not what a parser MUST do with a stream whose pad bits are not. Rejecting such a stream is the natural reading, so the suite asserts it, but at SHOULD, with the inference recorded in the assertion's `inferred_from`, and each such inference is raised as a request that the specification state the validator's rule. If it does, the case is re-issued at the stated level under a new id. `generators/SPEC-ISSUES.md` keeps the list. The test for whether a keyworded sentence binds a validator or only a producer is its subject and what it states. It binds a validator if its subject is a validator, a verifier or a verification procedure ("The SAID verification protocol MUST be implemented as follows"), or if it states a condition for a message to be valid ("to be valid, the ACDC node pointed to by this Edge MUST be a Targeted ACDC"). A sentence that defines a value, such as how a SAID is computed, binds a validator through a validator-facing sentence that requires checking that value. Any other keyworded sentence binds producers. The ACDC section, under "How levels are derived", applies this test with the rest of the grading rules. The KERI layer grades one more kind of inference the same way. The KERI specification states when a validator may accept an event but never that it must, so every assertion that a valid event is accepted is an inferred SHOULD, as described under KERI.

**Requirement levels attach to assertions, not to cases.** One case typically checks several things at different levels. An event delivered with too few signatures, for example, is checked for not being accepted when it arrives — a MUST, because the KERI specification forbids accepting an event whose signatures do not satisfy its thresholds — and for being accepted once the missing signatures arrive, which is only a SHOULD, because the specification says such an event SHOULD be escrowed rather than requiring it. Each assertion carries the clause it rests on and that clause's level: `MUST`, `SHOULD` or `MAY`. Only MUST assertions decide the verdict, but SHOULD and MAY results are reported beside it, and a conformance claim states its SHOULD results (see Versioning). A case with no assertion that rests on a clause does not belong in the conformance cases.

**Behaviour the specs do not define lives in named profiles.** keripy's escrow taxonomy, its error classes, its HTTP endpoints, the CESR 1.00 count-code table that keripy 1.x uses, and roles such as registrars and observers that have no specification yet are all real and all useful to test, but none of them is conformance. Cases for them belong to a clearly labelled non-normative profile, which reports interoperability with a named implementation and never claims more.

**Published expectations never change.** A case id is permanent, and so is every assertion in it. If a case turns out to be wrong, it is deprecated and a corrected case is added under a new id that the old one points to. A conformance reported against a suite release therefore never silently changes meaning, and an implementation that regresses between releases has changed, rather than the suite having moved under it.

**Fixtures are generated, never hand-edited.** Cases are produced from small declarative scenario files by generators. CI regenerates every case in a pinned environment and fails if any byte differs. Editing an expected value to make an implementation pass is therefore not just forbidden but impossible to merge.

**Anything but an answer is a failure.** An adapter declares the features its implementation supports when it starts, and the runner does not send a case that needs an undeclared feature; that case is recorded as `not-supported`. For every case the runner does send, the adapter must answer. A crash, a hang past the time limit, an oversized or malformed response, or an `unsupported` reply to a case it declared support for are all failures of every assertion in that case; so is a summary of an accepted stream given where decoded items were required. This matters most for the cases that matter most: a parser that panics or loops on a hostile stream fails the must-reject cases built to catch it, instead of disappearing from the tally. The only outcome that is not scored is a fault on the runner's side, such as being unable to start the adapter at all, and the runner retries such a fault before recording it.

**Results say whose logic was tested.** A library that verifies events but does not route, escrow or detect duplicity needs its adapter to supply that logic before it can run a KERI case. When an adapter does that, it declares which behaviours it composes, and the conformance report and any conformance claim say so: "conformant with the adapter composing escrow" is a different claim from "conformant". Otherwise a deployment of the bare library could be credited with behaviour only the adapter performs.

**Shared defects are flagged.** When keripy both produced a case's expected values and is the implementation under test, a pass proves only that keripy agrees with itself. The conformance report marks such passes as self-agreement.

## Layers and verdicts

Cases are grouped into four layers, each with its own operations in the adapter protocol and its own report shape. The KERI layer includes `exn.verify`, which checks KERI exchange messages; IPEX messages are tested through it, for the reasons the IPEX section gives, and the IPEX layer has no cases until IPEX has normative text.

### CESR

A CESR case gives a byte stream and asserts either its decoded structure or a rejection.

The stream is delivered as raw bytes, never pre-decoded or pre-split, so that a parser must find its own way in: sniff the domain of the first byte, find the boundary of each serialized message from its version string, and cross any switch between text and binary domains or between JSON, CBOR and MessagePack bodies.

The decoded structure describes the wire, not any implementation's object model. It is a sequence of items in stream order, each with its start and end offset in the stream. An item is one of:

- a **primitive**: its code and its raw value, in hex;
- an **indexed signature**: its code, its raw value, and each index field that its code's table entry defines on the wire — nothing an implementation infers;
- a **count code**: its code, the value of its size field exactly as encoded, and the offset at which its group ends;
- a **genus/version code**: its code, its genus and its version, which it carries instead of a size;
- a **serialized message body**: its protocol, version, serialization kind and declared size, for bodies framed by a version string (JSON, CBOR, MessagePack). A body in native CESR is reported as what it is on the wire: a count code followed by its primitives.

Offsets are how framing is checked. A count code's assertion includes the offset at which its group ends, so a parser that reads a size field as a number of items where the spec says quadlets ends the group in the wrong place and fails, even if it reports the raw size value correctly.

A rejection names a class — for example, truncated input, an unknown code, or a count that overruns the stream. The class is informative. An assertion that a stream must be rejected holds if the implementation rejects it, whatever class it reports.

Some implementations parse a stream correctly but never say where each item lay: they hand back decoded values without offsets. An adapter must not work the offsets out itself, from counts or code tables, because then the adapter's parsing is what gets tested. So reporting item extents is a feature, `cesr.item-extents`, and every case with a decoded-structure assertion requires it. An adapter without it may answer a stream its implementation accepts with a summary instead: the number of bytes consumed, and nothing about the items. A case whose assertions are all rejections does not require the feature, so such an adapter still gives real evidence where it matters most: a summary for a stream that must be rejected fails the assertion, because the implementation accepted it.

The CESR layer also has an encoding operation: given a code and raw bytes, produce the text or binary encoding.

### KERI

A KERI case delivers a sequence of messages, in order, to a fresh validator, and asserts what the validator did with each message and what it ended up believing. Line numbers in this section are of `spec/spec-body.md` in the KERI specification at tag v1.0.1, commit `71cb54eb`.

**Perspective.** What a validator should do depends on who it is: the same sequence can leave an event pending for an ordinary validator and accepted by a witness of that identifier. Every KERI case therefore states its perspective, and the first cases all take the perspective of an ordinary validator with no special relationship to the identifiers involved. Cases from the perspective of a witness, a delegator or a watcher follow, each stated as such.

**What MUST means here.** In the KERI layer a MUST assertion tests safety: the validator never accepts what the specification forbids, and drops what it says to drop. That includes the limits on superseding recovery. Rule C1 says that the root KEL of a delegation "by definition MUST be non-delegated therefore either A. or B. MUST be satisfied, or else the superseding rotation MUST be discarded" (line 1823). A non-delegated KEL is its own root, so for every KEL a rotation that tries to supersede an event outside rules A and B is discarded at MUST. A rotation signed with a stolen current key, trying to supersede an interaction that already lies before a later rotation, is refused at that level. Accepting valid events, which is liveness, is graded SHOULD, because no sentence obliges a validator to accept anything: the sentences that mention acceptance state preconditions for it (lines 1258–1264, 1612 and 1780). Each liveness assertion records that inference in `inferred_from`. One consequence is that a validator that accepts nothing passes every MUST assertion, so a conformance report and any claim made from it state their SHOULD results beside the verdict.

**Two readings.** Each message is reported by two readings. It is **seen** if the validator has accepted it into its copy of the KEL. The specification treats accepted and first seen as the same thing and makes it permanent: "Once an event has been first seen, it is always seen and can't be unseen" (line 1788). It is on the **trunk** if it lies on the KEL's undisputed path. An event that a superseding rotation displaces stays seen and leaves the trunk: "All the already-seen but superseded events in the superseded fork still remain in the KEL" (line 1799). **Superseded** therefore means seen and off the trunk; it is not a third value. A message that is not a key event, such as a receipt, is never on the trunk.

**Quiescence.** After each message is delivered, the implementation processes everything it can — including anything held in escrow that the new message unblocks — until nothing further changes. The adapter is responsible for driving the implementation to this point, and the adapter protocol requires it. A message's **initial** seen reading is taken at quiescence after its own delivery, and its **final** seen reading and its trunk reading at quiescence after the last message. Defining every reading at quiescence is what makes it a property of the implementation rather than of when an adapter happened to look.

**The decision procedure.** Each message's readings are determined by the first of these steps that applies. Each step cites the clause it rests on, and the generator records which step decided each message. The procedure keeps two kinds of failure apart. An intrinsic failure is a property of the message's own bytes, and nothing can cure it. A failure relative to the trunk, such as a prior digest that does not name the event on the trunk, can be cured, because later events or a supersession that changes the trunk can make the same message acceptable. Steps 2 and 3 judge a message against state, and they apply only when the validator holds that state. Until it does, the message falls through to step 4, and it is judged again at each later quiescence.

1. **Intrinsic failure.** The encoding does not parse, the SAID does not match the content, the fields violate the event's schema, or an inception's `d` and `i` differ where they must be equal (lines 1737 and 1381). The message is not seen. The specification requires these checks but does not say that a failing message is dropped, so only not-seen is graded.
2. **No verifiable controller signature.** The message carries no controller signature, or the validator holds the key state needed to verify it and none of its controller signatures verifies. The message is not seen and is **rejected**: a validator "MUST drop that message (i.e., not escrow or otherwise accept it)" (line 1266). This step comes before any conflict check, so a conflicting event carrying a forged signature is rejected, never treated as evidence of duplicity.
3. **Forbidden by state the validator holds.** The validator holds state of the identifier, or of its delegator, that forbids the event. That covers a non-establishment event in an establishment-only KEL (line 377), a delegated event whose delegator has the do-not-delegate trait (line 379), and any event after a non-transferable inception or an abandoning rotation (line 340). The message is not seen. In the first two cases it is also rejected, because their sentences say drop. The third says only that "no more key events MUST be allowed", so only not-seen is graded. When the state that would forbid the event is not yet held, as with a delegated inception that arrives before its delegator's KEL, this step does not yet apply.
4. **Not yet acceptable.** The message is sound in itself but cannot be accepted against what the validator has seen. Its signatures may not satisfy the signing or witness threshold (lines 1258–1264). Its prior event may not have been seen, or its prior digest may not name the event on the trunk (line 1737). A rotation's keys may not satisfy the pre-rotation commitment of the latest establishment event on the trunk (line 1494). Or the delegating seal may not have been seen (line 1612). The message is not seen. Whether the validator keeps it as **pending** is graded only for a signature or witness threshold shortfall, which "SHOULD escrow the event" (line 1266). That sentence is the specification's only escrow obligation.
5. **Conflict on the trunk.** A different event already lies on the trunk at the message's location. If the message is a rotation that rule A or B permits to supersede that event (lines 1806–1819, applied up a chain of delegators by rule C), the message is seen and on the trunk, and the displaced event and every event after it stay seen and leave the trunk. Otherwise the message is not seen. For a rotation that is a MUST, and the rotation is also rejected, since "the superseding rotation MUST be discarded" (line 1823). For any other event, such as a second interaction ("An interaction event may not supersede any event", line 1810) or a second inception, no keyworded sentence applies, so not-seen is graded SHOULD, inferred from rule A2 and from line 1799, which says such an event "cannot be first seen at all". The conflict is with the trunk, not with every seen event. After a recovery, a new event at a location held only by a superseded event extends the trunk and conflicts with nothing.
6. Otherwise the message is seen. A key event is then also on the trunk; a receipt or other non-key-event message is never on the trunk, as the Receipts section below says. A message identical to one already seen changes nothing.

**What is graded at which level.**

- **Not seen**, where a clause forbids acceptance, is a MUST. That covers every outcome of steps 1 to 5 except a conflicting event that is not a rotation, which is a SHOULD as step 5 says.
- **Rejected**, where a clause says drop, is a MUST, graded at the reading at which the clause applied when the message was delivered. A message that was kept and only later became subject to a drop rule — a delegated inception escrowed before its delegator's do-not-delegate trait was seen — is graded only as not seen, because the specification gives the re-evaluation of escrowed events no level.
- **Pending** is a SHOULD, for a signature or witness threshold shortfall only (line 1266).
- **Seen and on the trunk**, for a message the procedure accepts, is a SHOULD, inferred: this is liveness. So is accepting a rotation that rule A or B permits to supersede, with the events it displaces still seen and off the trunk. An event under its threshold that is finally seen once the missing signatures arrive, on a later copy or in a receipt, rests directly on line 1266 at SHOULD.
- **Escrow with no text** — keeping an out-of-order event, a delegated event awaiting its seal, or a receipt that arrives before its event (line 1286, "can escrow") until it can be used — is graded only in a named non-normative profile, at `INTEROP`. The safety half of such a case, that the early message is not seen on arrival, is still a MUST.
- **Duplicitous** is informative from a validator's perspective. The only sentence about keeping conflicting events (line 51) concerns watchers.

A MUST assertion is never gated behind a feature an adapter can decline. A case that checks that a superseding rotation is refused does not require `kel.recovery`, and a case that checks that an early event is not seen on arrival does not require `keri.escrow`; the liveness assertions that need those behaviours go in separate cases that do. Otherwise an adapter could decline a feature and skip a safety case.

**Key state.** A case asserts the final key state of each identifier involved: its sequence number, the SAID of its latest event on the trunk, its current signing keys and threshold, its next key digests and threshold, its witnesses and witness threshold, and its delegator if it has one. Those are the facts a relying party acts on. Every key-state assertion is conditional. It names one message, and says that if that message was finally seen, the identifier's key state is exactly this; if it was not, the assertion does not apply and is reported as `not-applicable`, neither a pass nor a failure. The assertion keeps the level of the clause that fixes the state's content, not the level of the acceptance it is conditioned on. After a rotation that breaks its pre-rotation commitment, for example, the assertion "if the inception was seen, the keys are still the inception's keys" is a MUST under lines 1262 and 1494, so an implementation that refuses the rotation but applies it to its state fails a MUST. Thresholds are compared after normalization by the runner, so that `"1"` and `"0x1"`, or a single weighted clause written with and without its enclosing list, compare equal; adapters report thresholds as their implementation holds them.

**Receipts.** A receipt is not a key event (line 1286), so it is never on the trunk. Its seen reading, whether the validator attached its signatures to its copy of the event (line 1782), is reported but graded only where a clause grades it. Cases grade a receipt by its effect on the event it receipts (lines 1264, 1266 and 1782). One sentence conflicts with that. Line 1266 says a validator MUST drop "a key event or non-key-event message that does not have attached at least one verifiable Controller signature". A receipt is a non-key-event message that carries witness signatures, not controller signatures, so read literally the sentence requires every witness receipt to be dropped, contradicting the same paragraph's completion of a threshold "to a receipt of that event" and lines 1286 and 1782. The suite applies the drop rule to key events only, records the conflict in `spec_conflicts` on every assertion that relies on a receipt, and raises it with the working group.

A message's report can also carry a reason, such as an unmet signing threshold or a broken pre-rotation commitment, and keripy's finer escrow categories (out-of-order, partially signed, partially witnessed, awaiting delegation). These are reported when an adapter supplies them and never decide a case.

**Emitting events.** The KERI layer also has an emitting operation: given raw key seeds and event parameters, produce the signed event. The assertions are that the event body is byte-for-byte what the specification's serialization rules determine, which includes its SAID; that every signature verifies against the stated keys; and that the attachments, once parsed, carry the same signatures with the same indexes. The framing of attachments is not asserted byte-for-byte, because the specification allows more than one valid way to group them. Cases supply raw private key seeds rather than salts, because salt-to-key derivation is a keripy convention and not part of the specification. Any timestamp an event carries is a fixed input.

Escrow timeouts are out of scope. Adapters drive each case synchronously, and no case depends on elapsed time.

### ACDC

An ACDC case presents one ACDC together with everything needed to judge it, and asserts whether it is valid, what its registry says, and whether each edge in its provenance holds. Line numbers in this section are of `spec/spec-body.md` in the ACDC specification at tag v1.0, commit `4a543c54`. "KERI line" refers to the KERI specification at tag v1.0.1, as in the KERI section, and "CESR line" to the CESR specification at tag v1.0, commit `03712960`.

#### The specification and the wire

The ACDC cases cite the released text, `trustoverip/kswg-acdc-specification` at tag v1.0, as the CESR and KERI cases cite theirs. That document is version 1.0 of the specification, but the wire protocol it defines is ACDC 2.00. Its version string has the form `ACDCMmmGggKKKKSSSS` (line 64), and its field set, its SAID rule and its registries are those of 2.00. The normative profile is named `acdc-1.0`, after the specification version, as `keri-1.0` is, and every case in it uses ACDC 2.00 bytes. The name is a hazard and is stated here so that nobody misreads it: the profile called `acdc-1.0` does not test what keripy 1.x calls ACDC 1.0.

What keripy 1.x calls ACDC 1.0 has almost no normative text. The specification requires an ACDC 2.XX implementation to support the old version string format "to properly verify Message bodies created with 1.x format events" (line 68), and says nothing more about those bodies. The 1.x field set, which has `ri` where 2.00 has `rd` and no `t`, the 1.x computation of the top-level SAID over the expanded form instead of the most compact one, and the 1.x issuance and revocation registry (`vcp`, `iss`, `rev`) carry no RFC 2119 keyword anywhere. Many deployments depend on them, so the suite tests them as it tests the CESR 1.00 count codes, in the non-normative profile `acdc-keripy-1x-interop`, whose assertions are graded `INTEROP` and which reports interoperability with keripy 1.x and nothing more.

A scenario is rendered in both profiles only when both renderings are decided at the same step of the decision procedure below, with the same verdict and the same facts. Its 2.00 rendering then goes into `acdc-1.0` and its 1.x rendering into `acdc-keripy-1x-interop`, and a result in one profile can be compared with a result in the other. A scenario whose 1.x form would be decided differently gets a separately named interop case instead. A directly sealed ACDC is the common example: keripy 1.x accepts issuance only through a `vcp`/`iss` registry, so its 1.x form is decided at the registry step and carries registry facts the 2.00 form lacks. A scenario about something with no 1.x form, such as the most compact SAID, blindable registries or selective disclosure, is rendered in 2.00 only.

The specification's main branch has moved past the tag. Its additions include requirements for bulk issuance that exist only there, and cases for them are issued as `draft`, pinned to the commit whose text they cite, until a tag carries that text. Main also adds worked examples that were produced by synchronising with keripy. The generator uses them as a cross-check and never as expected values, because a value keripy produced cannot show keripy wrong. The tag's own worked examples are part of the pinned text and are used as the text, with the weight the grading rules below give an example.

#### The bundle and the evaluation point

An ACDC is never valid on its own. Whether it is depends on its issuer's key state, its schema, its registry and the ACDCs its edges point to, which in turn depend on theirs, so a case gives the adapter a bundle that holds all of them:

- the KERI messages of every KEL involved, which are those of the issuer of every ACDC in the bundle, of any delegator, and of any issuee the case needs, delivered in order and processed as a `keri.process` request would process them;
- the registry events (`rip`, `bup`) of every registry an ACDC in the bundle names, each with its attachments, including any disclosed blinded state;
- the schemas, as compact JSON Schema documents, including any schema an edge names;
- every ACDC in the presented ACDC's provenance DAG: the far nodes its edges point to, the far nodes their edges point to, and so on to the leaves, each once however many edges point to it, each in the variant the case chooses and with the attachments that carry or point to its issuer's commitment;
- the presented ACDC, in the variant the case tests (compact, fully expanded, partially disclosed or selectively disclosed), with its attachments.

Nothing in the bundle is pre-parsed, for the same reason a CESR stream is not: the parser is part of what is tested.

The bundle holds the whole provenance DAG because whether an edge holds can depend on its far node, and that far node's edges on theirs. A multi-hop chain, such as the vLEI chain in which a role credential points to a legal entity's credential and that to a qualified issuer's, is therefore one case. The DAG is bounded, as every input the suite gives is: it holds at most 16 ACDCs, the presented ACDC included, its longest path from the presented ACDC has at most 8 edges, and the case schema refuses a case beyond either bound. Every node is identified by its SAID, so a cycle would need a SAID that is a digest of content containing itself. A validator that recomputes each far node's SAID therefore never meets a cycle, and a bundle whose `d` fields are forged to describe one fails at the recomputation.

The bundle is also the evaluation point. Whether an ACDC is valid depends on when the question is asked, because its issuer may later rotate keys and its registry may later record a change of state. A case fixes the moment by including only what has happened by then: the generator cuts every KEL and every registry at the evaluation point, and records the sequence numbers it kept, informatively, as `as_of`. No case depends on a clock. An adapter must not compare a `dt` field or an expiry attribute with the current time, and if its implementation does so, the adapter must fix the implementation's clock.

Because nothing outside the bundle exists for the validator, an anchor that is not in the bundle was never made, as far as the case is concerned. That is why the distinction between an invalid ACDC and an incomplete one, below, is never graded.

#### Verdicts

The adapter answers each case with one of three verdicts. `valid` means the ACDC verified. `invalid` means something in it, or something it depends on, failed to verify. `incomplete` means something it needs is absent from the bundle, such as its schema, its issuer's KEL, a far node or a registry event. The cases grade two values, valid and not valid. Both `invalid` and `incomplete` count as not valid, graded at the level of the clause that failed, and which of the two an implementation reports is informative, as every refinement the specification does not define is informative in the KERI layer.

There is no `revoked` verdict. No sentence in the specification says that an ACDC whose registry records a revocation fails validation, and the specification names `issued` and `revoked` only as examples of the states an issuance and revocation registry may use (line 2041). A suite that graded revocation as a verdict would be defining what revocation means, which is the working group's decision. What a registry says is still reported and graded, as facts, under Registry state below. What a validator should conclude from a revocation is tested only in a non-normative profile that follows a stated ecosystem convention. In the normative profile, a case whose registry records a change of state after issuance grades the registry facts and not the verdict.

Accepting a valid ACDC is graded SHOULD, inferred, as accepting a valid key event is in the KERI layer, because no sentence obliges a validator to accept anything. Two sentences require implementations to support something, and neither makes reporting `valid` a MUST.

ACDC 2.XX implementations "MUST support the old ACDC version 1.x Version String format to properly verify Message bodies created with 1.x format events" (line 68). That is a framing obligation: an implementation must parse a 1.x version string and frame the body it declares. It is graded as framing and nothing more, by a case whose presented ACDC carries a 1.x version string over bytes on which the 1.x and 2.00 rules agree (compact, with no `rd`, `ri` or `t`), followed by its attachments. The case's MUST assertion is that the adapter answers with a verdict rather than an error, and its verdict is the usual inferred SHOULD. A 1.x version string over a body that carries 2.00 fields is a body no implementation emits, and the text does not say whether "support the format" covers it, so no case grades it.

All ACDC implementations "MUST support any instance of an ACDC that employs the minimal Selective Disclosure mechanisms" (line 2735). Accepting a selectively disclosed ACDC depends on how its aggregate is computed, which the text pins only by a worked example (Construction properties, below), so that acceptance is graded SHOULD, inferred from line 2735 and the example.

#### What MUST means here

As in the KERI layer, a MUST assertion tests safety: an ACDC that the specification's validator rules say fails is not reported valid. The ACDC specification has fewer such rules than KERI, and the largest gap is in the place that matters most. No sentence with a keyword obliges a validator to refuse an ACDC its issuer never committed to. The sentence saying that the issuer must anchor an issuance proof (line 1663) has no keyword, and neither has the one saying that ACDCs are bound to the issuer's key state rather than signed (line 1673). The keyworded sentences nearby bind the issuer: line 1669 requires a registry's inception and updates to be anchored. The only keyworded sentence about the commitment itself, that the issuer "MUST provide a signature or seal on the SAID of the most compact form variant" (line 1843), binds the issuer too, and it sits in the IPEX section, which declares itself non-normative (line 1797), so no case cites it. A direct commitment refusal cites line 95, which makes the issuer's key state the one KERI establishes, with the inference through lines 1663 and 1673 recorded in `inferred_from`; a refusal through a registry cites line 1669. Refusing an ACDC with no issuer commitment is therefore an inferred SHOULD, and so is every refusal that rests on it: an ACDC whose only seal is in another identifier's KEL, whose attached seal reference names an event that does not carry the seal, whose registry was incepted by another identifier, or whose issuance or revocation is not anchored. The gap is `generators/SPEC-ISSUES.md` A-G1, a request for a sentence saying that a validator MUST NOT treat an ACDC as valid unless its issuer has committed to its most compact SAID. Until the specification says so, an ACDC conformance claim carries most of its meaning in its SHOULD results, which a claim always states.

The MUST assertions that the text does support fall into four groups. A SAID that does not verify against its content is one, whether it is the ACDC's own SAID, a nested block's, a schema's or a registry event's: CESR line 1194 says "The SAID verification protocol MUST be implemented as follows", and lines 134 and 147 fix the most compact form that an ACDC's SAIDs are computed over. An ACDC that does not validate against its schema is another (lines 246 and 250). An edge that fails the checks that lines 1174, 1178, 1199, 1201 and 1205 require of a validator is the third. Framing a 1.x version string (line 68) is the fourth.

A validator that accepts nothing passes every one of those MUST assertions. The KERI layer has the same property, and the ACDC layer has it more strongly, because nearly every refusal is an inferred SHOULD as well and an adapter that cannot evaluate something answers `incomplete`. So every ACDC refusal scenario is paired with a positive scenario that differs from it only in the defect: the same bundle with the seal present, the schema intact, or the far node correct. The generator refuses a refusal scenario that names no pair. A conformance claim reports the pairs' liveness results beside the MUST verdict, so an implementation that refuses everything shows as failing the valid half of every pair rather than passing the batch.

#### How levels are derived

Every assertion's level comes from the clauses it rests on, by the rules below, and the generator records for each assertion the derivation that set its level. The rules apply to the exchange-message cases as well.

Which clauses bind a validator is decided by the test that the principle "An obligation the specification states only for producers is graded SHOULD for validators" states. A keyworded clause binds a validator directly if its subject is a validator, a verifier or a verification procedure ("a Validator MUST confirm", line 1174; "The SAID verification protocol MUST be implemented as follows", CESR line 1194), or if it states a condition for the message to be valid ("to be valid, the ACDC node pointed to by this Edge MUST be a Targeted ACDC", line 1205). A clause that defines a value, such as the most compact SAID computation (lines 134 and 147) or an edge's effective operator list (lines 1199 and 1201), binds a validator through a validator-facing clause that requires checking that value, and a derivation that runs through both is graded MUST. Every other keyworded clause binds the producer. "MUST appear in any ACDC" (line 36) and "MUST appear in the following order" (line 32) describe what an issuer emits, so refusing an ACDC that violates them is an inferred SHOULD. The KERI layer grades a key event's field set at MUST through KERI line 1737's definition of a verifier, which counts "the appearance of fields" as structure a verifier checks, and the ACDC specification has no such sentence.

A refusal is a derivation: a chain of clauses from the check that fails to the conclusion that the ACDC is not valid, and each link has its own level. A derivation is only as strong as its weakest link, and an assertion that several independent derivations support is as strong as the strongest of them. So a not-valid assertion is graded at the highest, over the derivations that independently refuse the ACDC, of the lowest level along each derivation. An ACDC with no `s` field, for example, is refused by step 1 at SHOULD, inferred from line 36, and by step 2 through a one-link derivation at MUST under line 250, so it is graded MUST, while step 1 is still what the case records as the reason. A derivation counts only if its step can be evaluated on bytes an implementation could reach: when an earlier step leaves the bytes unframeable, the later steps are not evaluated. The rule is defined for edges combined with `AND`, explicitly or by default, and with no `NOT` operator. Under `OR` a refusal needs every member to fail, and `NOT` turns a far node's refusal into an edge's acceptance, so cases that use `OR`, `NAND`, `NOR` or `NOT` wait for a composition rule of their own.

A link that rests on MAY, or that the text leaves to an ecosystem governance framework (EGF), supports no normative assertion, so a derivation through one is not graded in `acdc-1.0`; where its conclusion is worth testing, a named non-normative profile grades it. A link that rests on an analogy ("A BLID is effectively a type of SAID", line 2066) or only on a worked example makes its derivation an inferred SHOULD, with `inferred_from` naming the analogy or the example.

Some computations the cases depend on are fixed by the text only up to a choice: the version string's size field and the JSON form of the most compact serialization, the aggregate's pre-image, the serialization a schema's SAID is taken over, and the primitive code of a blinded state's `ts`. Construction properties, below, lists each and the reading the generator uses. A refusal on such bytes stays MUST only if it holds under every candidate reading, which the generator checks, as the KERI generator checks every assertion under three keep policies. An acceptance that depends on the choice is graded SHOULD, with `inferred_from` naming the choice, and the choice is raised with the working group in `generators/SPEC-ISSUES.md`. Where a keyworded sentence and keripy disagree about bytes, as they do on the label of an update's transaction SAID field, the cases follow the sentence and keripy is disputed.

#### The decision procedure

The verdict is decided by the first of these steps that applies. Each step names the clauses it rests on and the level they give it, by the rules above, and the generator records which step decided each case.

1. Intrinsic failure. If any SAID in the presented ACDC does not verify against its content, including a top-level `d` that is not the SAID of the most compact form, the ACDC is not valid at MUST: CESR line 1194 makes the verification protocol a validator's obligation, and lines 134 and 147 fix the most compact form that the SAID is taken over. That includes an ACDC presented fully expanded whose `d` was computed over the expanded bytes, which is keripy 1.x's rule. Line 136 says to verify by first expanding "a given block", without saying block-level; the cases follow the keyworded sentences at lines 134 and 142 and record line 136 in `spec_conflicts`. If the version string does not parse or does not name ACDC (line 64), if the top-level fields are out of order or a required field is missing (lines 32 and 36), or if the ACDC has both a non-empty `a` and a non-empty `A` (lines 106 and 110), it is not valid at SHOULD, inferred, because those sentences bind the producer. Nothing else in the bundle can cure an intrinsic failure.
2. Schema. The schema whose SAID is the ACDC's `s` field must be in the bundle and must verify against that SAID (lines 186 and 248; CESR line 1194), and the ACDC must validate against it in one of the variants its composition allows (line 246). Failing any of these makes the ACDC not valid at MUST, because line 250 requires that compliance "MUST be enforced by validating against the composed Schema", which a validator without a schema of the right SAID cannot do. A schema in the bundle whose `$id` holds a different SAID does not stand in for the right one, which is how a substituted schema is caught. A schema that uses a dynamic reference or a non-local `$ref` makes the ACDC not valid at SHOULD, inferred from lines 194, 206 and 220, which bind schema authors. A `$schema` that names a dialect other than JSON Schema 2020-12 makes it not valid at SHOULD, which line 226 states directly.
3. Issuer key state. The validator establishes the issuer's key state from the KELs in the bundle by KERI's rules (line 95: "The verifiable key state for AIDs MUST be established with the KERI protocol"), so an event the KERI layer would not see does not count here either. If the issuer's inception is not seen, the ACDC is not valid. The level is SHOULD, inferred, because the issuer's key state matters only to the commitment in step 4, and no keyword sentence requires that commitment.
4. Issuance commitment. The issuer must have committed to the ACDC's most compact SAID, either by a seal of that SAID in a key event that is seen and on the trunk of the issuer's KEL, or through an event of the ACDC's registry that names it, verified in step 5. A reference attached to the ACDC that names the sealing event is a pointer ("This reference MAY be attached to the presentation", line 1671). The seal must be found in the event the reference names, or elsewhere on the issuer's trunk, and a reference to an event that does not carry the seal, or whose digest does not match the event at its sequence number, commits nothing. If no commitment holds, the ACDC is not valid at SHOULD, inferred from line 95 through lines 1663 and 1673, which bind an ACDC to its issuer's key state only by such a seal.
5. Registry. When the ACDC has a top-level registry field, `rd`, the validator verifies that registry's events in order and reports its head state, as Registry state describes. The registry inception must be sealed in the issuer's KEL and must name the issuer (lines 1669 and 2015). Each later event must name the registry (line 2019), carry the next sequence number (line 2023) and the SAID of the event before it (line 2027), verify against its own SAID (CESR line 1194), and be sealed in the issuer's KEL (lines 1669 and 1922). The verified chain runs from the inception to the last event before the first one that fails, and no event after a failure counts, so an issuance event that is not sealed, or is sealed only in another identifier's KEL, issues nothing even when the inception before it is sound. A disclosed blinded state block is checked two ways, which cases keep apart. A block that does not hash to its own BLID fails as a SAID would, but the text makes a BLID a SAID only by analogy: "A BLID is effectively a type of SAID" (line 2066), and its computation "follows the SAID protocol, adapted for fixed-field representations" (line 2141). So that refusal is an inferred SHOULD. A block that is consistent with its own BLID, where that BLID is not the update's `b` field, was never committed by the update, which is also an inferred SHOULD (line 2066). If the ACDC relies on its registry for its commitment and no event in the verified chain names it, the ACDC is not valid at SHOULD, inferred from line 1669, which binds the issuer to anchor the updates through which a registry commits to an ACDC.
6. Edges. The validator evaluates every edge in the provenance DAG, as Edges describes, and each edge is graded on its own checks. What an edge's failure means for the ACDC is not graded in `acdc-1.0`, for the reason Edges gives.
7. Otherwise the ACDC is valid, graded SHOULD, inferred. A case whose provenance DAG holds a failing edge or a node that is not valid does not grade the presented ACDC's verdict in `acdc-1.0`.

Step 1 is the only step that judges the presented bytes alone. The others judge the ACDC against the rest of the bundle, and a different bundle could pass it.

Commitment by issuer signatures alone is outside the first batch. The only text that admits it, line 1843 ("a signature or seal"), sits in the section that line 1797 declares non-normative, while normative text says that "ACDCs are not directly signed by the Issuer" (line 1673). The text also leaves open which establishment event such a signature must name. No case grades signature-only issuance either way until the working group says whether a signature alone commits an issuer, and if it does, which establishment event the signature must name (`generators/SPEC-ISSUES.md`, A-G3). An implementation that sees such a commitment and cannot evaluate it answers `incomplete`.

#### Registry state

When the presented ACDC names a registry in its top-level `rd` field, the adapter reports the verified head of that registry: the registry's SAID (`rd`), the sequence number and SAID of the last event in the verified chain (`n` and `d`), and that event's transaction ACDC SAID and state (`td` and `ts`). For a blindable update whose blinded block is not disclosed, `td` and `ts` are reported as unknown. These are the facts a relying party acts on, and the specification fixes them through the registry chain rules in step 5, so they are graded, but as facts rather than as a verdict.

A registry-state assertion is conditional, like a KERI key-state assertion. It says that if the adapter reports a registry for the ACDC, the head is exactly this; if the adapter reports none, the assertion is not applicable, unless its verdict is `valid` (see below). It takes the level of the clause that fixes the state's content, not the level of the acceptance it is conditioned on. Most of those clauses bind the issuer, so most registry-state assertions are SHOULD, inferred. Where the content is decided by a SAID check, as when an update that does not verify against its own SAID must not advance the head, the assertion is MUST under CESR line 1194. A separate assertion grades whether the registry is reported at all. Reporting a valid registry is liveness, graded SHOULD, inferred. Reporting no registry when its inception is not sealed by the issuer is a refusal, graded SHOULD, inferred from lines 1669 and 2015. A validator that reports no registry for anything makes every state assertion not applicable and fails those SHOULD assertions, which a conformance claim states. A `valid` verdict, though, commits the adapter to the registry it relied on: when the presented ACDC names a registry and the adapter answers `valid`, it must report that registry's head, and a `valid` verdict with no registry reported fails every registry-state assertion in the case, MUST included. So an adapter cannot hide a head that a failed update wrongly advanced by declining to report it while still vouching for the ACDC. Only a verdict other than `valid` releases it from reporting.

The first batch tests blindable registries only. Non-blindable updates (`upd`) are added when an implementation verifies them. Their keyworded field list names the transaction SAID field `ta`: the fields "MUST appear in the following order, `[v, t, d, rd, n, p, dt, ta, ts]`" (line 1993). A heading and a cross-reference call it `td` (lines 2035 and 2060), as keripy does. The cases will follow line 1993, record the other lines in `spec_conflicts`, and expect keripy to be disputed. The report calls the value `td` whatever its wire label, because the report's field names are the suite's.

The report covers only a registry named by a top-level `rd`. The text also allows an ACDC's registry to be named elsewhere: line 85 says the field "Typically" appears at the top level, line 174 allows it inside `a` or `A` for bulk issuance, and line 2389 ties `rd` to secure discovery. An ACDC bound to a registry without a top-level `rd` is outside the first batch, and the report's shape will be extended before the first case that needs it.

Registries in which two events claim the same sequence number are not graded, because nothing in the specification says what a validator should do with them. They belong to a non-normative profile.

#### Edges

The specification requires a validator to check an edge in these ways. The far node the edge names must be in the bundle, and its SAID, recomputed from its content, must equal the edge's `n` field. It must validate against its own schema, and against the edge's schema `s` when the edge has one (lines 1174 and 1178). The edge's operators then apply. When the edge names no issuer operator, `I2I` is appended if the far node has an issuee and `NI2I` if it has none (lines 1199 and 1201), and `I2I` requires the near node's issuer to be the far node's issuee (line 1205). The members of an edge group are combined with `AND` when the group names no operator (line 1110). A far node presented in a variant that hides whether it has an issuee, with its `a` compact or its issuee block blinded, leaves lines 1199 and 1201 undecidable, so the edge cannot be confirmed valid. An edge that fails any of these checks is not valid at MUST.

The adapter reports each edge it evaluated, anywhere in the provenance DAG, identified by the SAID of its near node and the label path from that node's top-level `e` field (for example `e.le`), together with the far node's SAID and whether it found the edge valid. Keying an edge by its near node keeps apart two nodes' edges that share a label, and in a diamond, where two near nodes point to one far node, each edge is still one entry.

An edge assertion is conditional on the adapter reporting that edge, as a registry-state assertion is conditional on a reported registry, and is not applicable when the edge is not reported. Whether an edge is reported at all is graded separately, at SHOULD, inferred, and requires `acdc.edges`: every edge is expected to be reported in a case whose DAG is wholly valid, and in a case built around one failing edge, that edge is. A validator that never reports edges therefore makes every edge MUST not applicable and fails those SHOULD assertions, which a conformance claim states. The same commitment applies to edges. In a case built around a failing edge whose check is a MUST, a reported edge is graded on what the adapter reports for it, so reporting the failing edge as valid fails the assertion whatever the verdict. If the edge is not reported, the assertion holds when the verdict for the presented ACDC is not `valid` and fails when it is. A validator may still find the near node valid, since propagation is the governance framework's choice, but it must then show that it checked the edge, and an adapter whose implementation cannot evaluate edges answers `incomplete` for an ACDC that has them. An edge is graded valid, at SHOULD, inferred, only in a case whose DAG is wholly valid, so that a validator that stops at the first failure, or short-circuits a group, is never charged with edges it had no reason to evaluate.

Only an edge's own checks are graded. Line 1114 says "When any node in a provenance chain is invalid, an Edge pointing to that node MAY also be invalid. If a node has an invalid Edge, then the node MAY also be invalid", and the sentences after it that make a broken chain invalidate its head begin "Typically, in a given EGF (ecosystem governance framework)" (lines 1114 and 1116). The `NOT` operator inverts a far node's validity outright (line 1211). So in `acdc-1.0`, a far node that is not valid for a reason outside the edge's own checks, such as having no commitment from its own issuer, does not make the edge not valid, and a near node with an invalid edge may be reported valid or not valid. Both are informative. The non-normative profile `acdc-chain-strict` grades the reading many ecosystems adopt, in which every node and edge from the head of a chain to its tail must be valid for the head to be valid, at `INTEROP`.

#### Construction properties

Some properties of ACDCs are checked by construction: the generator computes the values from the specification's rules, with its own BLAKE3, and the cases assert them or depend on them. These are the SAID of every block by the most compact form algorithm (lines 134 and 147), so that the compact, partially disclosed and fully expanded variants of one ACDC share one top-level SAID; the aggregate (AGID) that commits to a selectively disclosable attribute list (lines 714 and 720); the BLID of a blinded state block (lines 2058, 2066 and 2141); and the SAID of every schema, by the CESR SAID protocol. keripy main cross-checks each of them byte for byte, as it does KERI bodies, and a disagreement is recorded in `generators/DISAGREEMENTS.md` without changing an expected value.

The text leaves the bytes of several of these computations open. The generator fixes them as follows, each is graded by the rule for unpinned bytes above, and each is raised in `generators/SPEC-ISSUES.md`.

- The most compact form is a serialization that the presented bytes need not contain, so its bytes are computed, not received. Lines 134 to 147 describe compaction and say nothing about the version string's size field or the JSON form. The generator gives `v` the compact serialization's own size, because line 62 says the field gives the size of the serialization, and serializes compact JSON with no whitespace, in UTF-8 with non-ASCII characters unescaped, as the worked examples do (CESR lines 1276 and 1289; ACDC line 3395). First-batch attribute values are ASCII, so escaping cannot decide a case.
- The aggregate. Line 110 calls it "a cryptographic digest of the concatenation of an ordered set of the SAIDs" of the blinded attribute blocks, while line 714 serializes the list, with a dummied first entry, "as a list in whatever serialization kind is used by the enclosing ACDC". Neither has a keyword. The tag's own worked example settles the JSON case: its pre-image at lines 951 to 956 is a compact JSON list of four entries for three blocks, the dummy first, and its digest is the AGID the example states, while a bare concatenation of the SAIDs gives a different digest. The cases follow line 714 and the example and record line 110 in `spec_conflicts`. Because the reading rests on an example, accepting a selectively disclosed ACDC is graded SHOULD, as Verdicts says.
- Schemas are delivered as compact JSON, so the bytes received are the serialization that the `$id` SAID is computed over, under either reading of CESR line 1194: the bytes received, or a re-serialization of them. Schemas in use are often distributed pretty-printed, and for those the two readings differ; a case that delivers one grades the schema's SAID at SHOULD.
- The `ts` field of a blinded state block is a CESR primitive "appropriate for" a state string (line 2062), and only the empty placeholder's code is fixed (line 2087). The generator uses the Tag codes, as keripy does. A BLID is computed over the bytes received, so verifying one does not depend on the code, but reporting `ts` does, and a `ts` fact is graded SHOULD, inferred, naming the choice.

A tamper never changes framing by accident. A scenario that alters a field either preserves the body's length or recomputes the version string's size, and records which, so that a case meant to test a SAID tests the SAID and not the framing. A case that tests framing does so deliberately, under a clause of its own.

Disclosure forms are tested through these properties. A compact ACDC and its expanded form must have the same SAID, a selectively disclosed attribute block must verify against the aggregate, and a partially disclosed chain must still verify through its edges. Chain-link confidentiality and contractually protected disclosure have a protocol half, which belongs to IPEX, and a legal half, whether the terms bind anyone, which no test can check.

#### Schemas

Expected schema verdicts need a JSON Schema 2020-12 evaluator, and the generators use only the Python standard library so that no implementation decides an expected value. The generator therefore implements a declared subset of JSON Schema: `type`, `properties`, `required`, `oneOf`, `anyOf`, `const`, and `$ref` to a location inside the same schema. It refuses a scenario whose schema uses any other keyword. The one exception is a schema built to be refused in step 2 because it uses a non-local or dynamic reference; the generator recognizes such a reference and decides the case without evaluating the schema. Every schema verdict is cross-checked against keripy's validator, and a disagreement is investigated, never adopted. The risk is that a bug in the subset evaluator becomes an expected value wherever the cross-check happens to agree with it, and a schema that needs a keyword outside the subset cannot be tested until the subset grows.

#### Features

Every ACDC case requires the KERI base features and `acdc.version-2.x`. The other ACDC features, `acdc.edges` and `acdc.registry.bup`, mark behaviour that an implementation may lack without breaking a MUST, so each is a feature an adapter can decline, like `keri.escrow`. Only liveness assertions, and the assertions that an edge or a registry is reported, require them. `acdc.registry.upd` is added with the first non-blindable registry cases, and `acdc.signed` only if the working group settles signature-only issuance. Selective disclosure has no feature, because line 2735 requires every implementation to support it, and neither does the legacy version string, because line 68 requires it of every 2.XX implementation.

A MUST assertion is never gated behind a declinable feature, here as in the KERI layer. A case that checks that a broken edge is not valid does not require `acdc.edges`, because delivering the bundle needs nothing the implementation can decline. An implementation that cannot evaluate part of a bundle, whether a kind of registry, an edge operator or a kind of commitment, must answer `incomplete` and never `valid`, which is failing closed. A scenario whose liveness assertions need a declinable feature and which also has MUST assertions is split, as in the KERI layer: its MUST assertions move to an ungated companion case with the same bundle.

#### The first batch

The first ACDC batch, `cases/acdc/` from `scenarios/acdc/`, covers each step of the decision procedure for directly sealed and registry-issued ACDCs in the 2.00 wire: framing, field rules and SAIDs, including a top-level SAID over the expanded form; the schema an ACDC names, its SAID, its references, its dialect and validation against it; the issuer's key state and commitment, including references that point at the wrong event; a blindable registry's chain and the head it gives, including updates that are unsealed, out of sequence, wrongly chained or that fail their SAID, and disclosed states that fail their BLID; each edge's own checks with the `I2I` operator named explicitly, over one-hop and two-hop chains and a diamond; and one selectively disclosed aggregate. The generator, `generators/spec_tables/acdc_cases.py`, runs a model of the decision procedure (`acdc_model.py`) over each bundle's bytes under every candidate reading of the open bytes, and refuses a scenario whose expected failures differ from the model's, a refusal without a positive pair, and a MUST refusal that some reading would accept. It records each assertion's derivation in its note and each refusal's pair in its description.

It leaves for later batches: the legacy version string (line 68), which needs an assertion that an answer was given and builder support for 1.x bodies; renderings in `acdc-keripy-1x-interop` and `acdc-chain-strict`; edges whose operators are not an explicit `I2I`, and the group operators that wait for the composition rule above; non-blindable registries, signature-only issuance, bulk issuance and registries named other than by a top-level `rd`; aggregate refusals; and the further cases listed under these headings. keripy main cross-checks every SAID, BLID and schema verdict in the batch (`generators/DISAGREEMENTS.md`).

### IPEX

The ACDC specification's IPEX section declares itself non-normative ("This section is non-normative", line 1797), although it contains sentences with keywords (lines 1807, 1822, 1828 and 1843), and the separate IPEX draft is informational. A section that disclaims normativity cannot support a conformance assertion, so no conformance case cites it. Its keyword sentences are triaged `practice` and are tested, if at all, by practice cases in a non-normative profile (see Practice). IPEX messages are KERI exchange messages, and KERI's text about them is normative: the fields of an `exn` message and their order (KERI line 1197: "No other top-level fields are allowed (MUST NOT appear)"), the prior-message field `p` (KERI line 975), and the exchange identifier `x`, which "MUST be the SAID, `d` field value of the first message in the set of exchange messages that constitute a transaction", that message being "an Exchange Inception message with type `xip`" (KERI line 979).

IPEX messages are therefore tested as exchange messages, graded against those clauses through the `exn.verify` operation. Because every clause these cases cite is KERI's, they belong to the KERI layer: they carry KERI case ids and sit in the `keri-1.0` profile. An implementation of KERI alone then gets exchange-message coverage, and an `acdc-1.0` result never implies that IPEX was tested. The IPEX layer holds only cases that rest on IPEX's own text, and it has none until IPEX has normative text. The ACDC that an IPEX grant carries is graded by `acdc.verify`, in a case of its own.

An `exn.verify` case delivers the KELs of the parties and then a sequence of exchange messages, and asserts whether each message is accepted, read twice: at quiescence after its own delivery and after the last message. An assertion that a message must be dropped holds only if both readings say it was not accepted, so an implementation that accepts a forged message on arrival and retracts it later still fails. A message is decided by the first of these steps that applies.

1. Intrinsic failure. If the message's SAID does not verify, it is not accepted, at MUST (CESR line 1194). If its fields are not exactly the set and order that KERI line 1197 (for `exn`) or KERI line 1154 (for `xip`) gives, it is not accepted, at MUST, on the same reasoning that grades a key event's field set in step 1 of the KERI procedure: a validator MUST act as a verifier, and verifying a message's structure includes "the appearance of fields" (KERI line 1737). A message the implementation cannot parse or frame is answered `rejected`, never with an error.
2. No verifiable sender signature. The sender is the AID in the message's `i` field. If the message carries no signature by the sender, or none of the sender's signatures satisfies the signing threshold of the sender's establishment event it references, it is not accepted, at MUST. Such a message is a non-key-event message that a validator "MUST drop" (KERI line 1266), its signatures "MUST at least satisfy the signing threshold for the establishment event indicated by the event reference" (KERI line 1260), and a verifier "MUST first determine which set of keys are or were the controlling set for the AID of that event" (KERI line 1737). A valid signature by another AID, naming that AID's own establishment event, is therefore not a signature by the sender.
3. Broken transaction link. If the message's `p` is not the SAID of the message before it in the transaction, or its `x` is not the SAID of the transaction's `xip`, or the message is outside any transaction and its `x` is not empty, it is not accepted, at SHOULD, inferred from KERI lines 975 and 979, which bind the sender.
4. Otherwise it is accepted, graded SHOULD, inferred, as liveness is everywhere else.

An implementation that starts a transaction without an `xip` message is disputed against KERI line 979, not excused, because the suite's authority is the text. A lone `exn` with an empty `p` and a non-empty `x` is refused under either reading of whether it belongs to a transaction. Outside a transaction, line 975 requires `p` to be empty and line 979 requires `x` to be empty too ("When an exchange message is not part of a transaction, the Exchange Identifier, `x` field value, MUST be the empty string"); inside one, line 979 requires an `xip` to have come first. The text does not say which reading a validator should take, and the case does not depend on it.

Which IPEX message may validly follow which, and when a message opens a new exchange rather than continuing one, is not stated anywhere normatively. Transcript cases that classify each message as a valid or invalid next step will be added when a normative transition rule exists to cite, and belong to a non-normative profile until then. Writing them now would make the suite the specification of IPEX's state machine, which is the working group's decision to make.

### Roles

What a role must believe is tested through ordinary KERI cases taken from that role's perspective: witness thresholds and receipt validity under KAWA (KERI's Algorithm for Witness Agreement, defined in the KERI specification); duplicity detection and first-seen behaviour for a watcher given divergent KELs from different sources. How a role behaves as a running service depends on a transport the specifications do not define, so tests of that kind — a witness serving receipts over keripy's HTTP interface, for example — belong in a non-normative profile.

## Cases

Each case is one JSON file, at `cases/<layer>/<id>.json`. Case ids are a layer prefix and a four-digit number — `CESR-0001`, `KERI-0001`, `ACDC-0001`, `IPEX-0001` — assigned in order and never reused. The number carries no meaning; the file's metadata does.

A case records:

- `id`, `title`, and a short `description` of what it tests and why.
- `status`: `active`, `draft`, `disputed`, or `deprecated`.
- `profile`: the profile the case belongs to.
- `targets`: the wire versions its inputs use, and the `features` an implementation must support to run it.
- `input`, including the perspective and evaluation point where they apply.
- `assertions`: each with what it checks, the expected value, the clause it rests on as a link to a stable anchor in a pinned specification commit, and that clause's requirement level.
- `provenance`: the scenario and generator that produced the case, and the implementation and commit that produced its expected values — or, for values derived directly from a specification, the specification commit.
- For a deprecated case, `superseded_by`; for a disputed case, a `dispute` record giving the clauses involved, what keripy does where that is the question, and where the question was raised.

## Scenarios and generators

A scenario is a small declarative file, under `scenarios/<layer>/`, that describes cases without their bytes: which identifiers exist, which keys they use, which events are built and in what order they are delivered, what tampering is applied, and which decision-procedure step each message is expected to reach. A generator turns scenarios into cases. The CESR and KERI generators build bytes from the specification itself: the CESR one from its code tables, the KERI one from its field rules with its own Ed25519 and BLAKE3, each checked against published test vectors. keripy is a cross-check rather than the source (`generators/keripy_keri_check`): it rebuilds every untampered KERI body byte for byte, verifies every signature, and replays each case, and a disagreement is recorded in `generators/DISAGREEMENTS.md` without changing an expected value.

A generator does not take keripy's word for a disposition. It computes each disposition from the decision procedure and the scenario, uses keripy to produce the bytes and to cross-check, and records any disagreement between keripy and the procedure as a candidate dispute for a maintainer to review. That matters because keripy's behaviour does not always match the procedure, and when it does not, the difference is exactly what the suite exists to surface.

Generators must be deterministic. Keys come from fixed seeds, timestamps are fixed, and a generator records its own version and the commit of whatever it drove. CI regenerates every case from its scenario and fails on any difference.

## Targets and profiles

Cases identify what their inputs are by the protocol versions that appear on the wire, not by implementation release numbers, which are ambiguous — keripy's 2.x release line implements version 1.0 of most of the specifications, and the wire format it emits by default carries version 2.00 codes.

A **profile**, under `profiles/`, is a named set of cases that an implementation can claim: "passes every active MUST assertion in profile P", stated together with its SHOULD results. A profile's status comes from the maturity of the text its assertions cite, not from the wire version of its inputs. The specifications at version 1.0 define the 2.00 code tables and require 2.XX implementations to accept 1.XX version strings, so cases built on those clauses are normative and active, including the count-code cases that motivated the suite. Where expected values come from an implementation whose behaviour is still moving — keripy's main branch, for example, ahead of a release — the case is `draft`, pinned to the commit it was generated from, and its results are advisory until it is regenerated against a release.

Some behaviour that many deployments depend on has no normative text: the CESR 1.00 count-code table used by keripy 1.x, for example, and the ACDC field set, SAID computation and registry that keripy 1.x uses. The suite tests it anyway, in profiles named for what they are, `keripy-1x-interop` and `acdc-keripy-1x-interop`, so that nobody mistakes passing them for conformance. The same goes for a reading the specification leaves to an ecosystem governance framework, such as a provenance chain that must be valid from head to tail, which `acdc-chain-strict` tests. A profile named for a specification version, such as `acdc-1.0`, is named for the text its assertions cite, not for the wire version of its inputs; `acdc-1.0` tests ACDC 2.00 bytes, as the ACDC section explains.

## Practice

Much of what deployments depend on has no normative text. The ACDC specification's IPEX section declares itself non-normative although it carries keyword sentences, the separate IPEX and PTEL drafts are informational, governance frameworks such as the vLEI ecosystem governance framework add rules of their own, and implementations share behaviour that no clause states. None of it can support a conformance assertion, but treating it as out of scope would read as "does not matter" and would leave untested the part of the protocol most deployments exercise. Folding it into conformance would make the suite the specification. So common practice is a tested tier of its own, kept apart from conformance in three places.

- **In clause coverage.** A keyword sentence in a section that disclaims normativity, or one that otherwise states common practice rather than a requirement, is triaged `practice`. It is reported in its own part of each coverage report and its own rows of the summary, and never counted among the obligations (see Clause coverage).
- **In cases.** A practice case belongs to a non-normative profile, and its assertions are level `INTEROP`, with a `basis` instead of a clause. A basis is a sentence saying what the assertion rests on; when it rests on a sentence of a pinned text, it is an object that also quotes that sentence with the same `spec`, `section`, `url` and `commit` fields a clause has, so that clause coverage can count the sentence as covered. Behaviour with no sentence at all is to be recorded in a practice catalogue, so that it is counted somewhere; the catalogue is not built yet, and is tracked as tick ~3lx6.
- **In the verdict.** A non-normative profile's run gets an interoperability verdict, described below, and never a conformance one.

A practice's basis must cite an informational text, a governance framework, or agreement between at least two independent implementations. "keripy does it" alone is never a basis, because the principle that the spec text is the authority exists to stop the suite enshrining keripy as law. Common practice is contestable, so every practice case states its basis and a reader can disagree with it. The tier starts with IPEX, which deployments depend on and where the gap between practice and normative text is widest; starting with one protocol keeps the tier from growing into everything an implementation happens to do.

**The interoperability verdict.** A profile is normative exactly when every assertion in it cites a clause, so a run whose assertions are all `INTEROP` is a run of a non-normative profile. Its verdict comes from its active `INTEROP` assertions, by the same rule a conformance verdict applies to MUST assertions: `not-interoperable` if one failed, `incomplete` if none failed but one could not be evaluated, `no-evidence` if none passed or failed, and `interoperable` otherwise. Its exit codes are those of the conformance verdicts in the same position: 0 for interoperable, 1 for not-interoperable, 4 for incomplete and 5 for no-evidence. Any other run is judged on its MUST assertions as before, and the report and printed summary show its `INTEROP` results and their interoperability verdict beside the conformance verdict, never affecting it. Like a conformance verdict, an interoperability verdict is scoped to the cases the adapter's declared features let the runner send.

## Versioning

Three things are versioned, and every conformance report states all three.

**The suite** uses semantic versioning. Adding cases is a minor release. Deprecating cases, or changing the adapter protocol incompatibly, is a major release. Changes to documentation and metadata are patches. Because assertions never change in place, a minor release can only add cases; it can make an implementation that previously passed everything fail a new case, but it cannot turn an old pass into a failure.

**The adapter protocol** has its own version, declared in the handshake. The runner accepts the current protocol version and the one before it, so adapters maintained outside this repository have a full major cycle to catch up.

**An adapter** follows its implementation's release line, because that is what its users will pin, and reports the exact implementation commit it was built against.

A conformance claim is therefore a tuple: suite version, profile, adapter version, implementation commit, the list of behaviours the adapter composes, if any, and the number of active SHOULD assertions that passed and that failed. A claim never states the MUST verdict alone. In the KERI layer, where accepting a valid event is a SHOULD, a validator that accepts nothing passes every MUST assertion, and only its SHOULD failures tell it apart from a working one. The runner's report and its printed summary carry those counts, and say so explicitly when any SHOULD assertion failed.

## The runner

The runner, `kcs`, is a Python package (Python 3.12 or later, managed with uv) with **no runtime dependencies**. That is deliberate. It must install wherever an adapter author works, whatever language their implementation is in, and it must never pull in an implementation under test, which is what would happen if it depended on keripy or on a CESR library. Generators, which do drive keripy, run in their own pinned environments and are not part of the runner.

The runner treats every adapter as untrusted code, because adapters run implementation code against hostile inputs and a parser bug can be exploitable. It bounds each response's size and each request's time, reads responses line by line with a size cap rather than buffering until a newline that may never come, and kills the adapter's whole process group on a violation. It also caps the adapter's memory and CPU time with resource limits, starts it with a scrubbed environment so it inherits no credentials, and refuses to run as root. The runner supports POSIX systems only, because its containment depends on POSIX process controls, and it refuses to start elsewhere. Network isolation is not something it can impose itself; CI provides it by running adapters, and above all the nightly runs against development heads, in jobs that hold no secrets and no write token.

### Checking an adapter

An adapter is a contract that people outside this repository implement, in several languages, so they need a way to check their adapter before they ever run a case. The suite provides two:

- **Message schemas.** `schema/adapter-protocol.schema.json` describes every request and response in JSON Schema, so an adapter author can validate their own messages in their own test suite, in any language.
- **`kcs check-adapter`.** This runs a fixed set of probes against an adapter and reports each one: the handshake is well-formed and its features are in the vocabulary; responses echo request ids; a malformed request gets an error response rather than a crash; and two invariants the adapter protocol requires and the runner otherwise cannot see. **Statelessness:** the probe creates an identifier in one request and, in the next, delivers an event for that identifier that a fresh validator must not accept; an adapter that leaks state between requests accepts it. **Quiescence:** the probe delivers a sequence in which a later message's disposition depends on whether an escrowed event was promoted first, so an adapter that does not drain escrow after each message reports the wrong disposition.

The runner also runs the statelessness probe at the start of every session, and can run a profile's cases in a shuffled order and compare the results with the ordered run, which catches state leaking between real cases.

## Adapters

An adapter is a small standalone program that connects one implementation to the runner. Adapters build against a released or pinned version of their implementation and use only its public API. They never patch the implementation. Where it lacks something a case needs, the adapter composes it on top and declares that it has done so. That way an adapter keeps working whether or not the implementation's maintainers ever choose to host it, and its results stay honest about what was tested.

Adapters start in this repository under `adapters/<name>/`, each self-contained so it can be lifted into its implementation's repository unchanged. The keripy adapter stays here permanently, because keripy is also a generator.

## Clause coverage

A list of cases cannot say where the suite is thin, so the suite also measures which normative sentences its cases test. `scripts/clause-coverage` enumerates every sentence of each pinned specification text that carries an uppercase RFC 2119 keyword, maps each assertion's clause and inference quotes onto those sentences, and writes a report per specification under [`coverage/`](coverage/README.md), which that directory's README explains how to read. The report is generated, never edited, and CI fails when it is stale. It counts only the public cases in this repository, so it reveals nothing about an embargoed one.

Beside each clause registry, `scenarios/<layer>/triage.json` records a hand-kept judgment of each sentence: whether a validator can be tested on it through an adapter, whether it binds a role no adapter plays and is out of scope, or whether no case could test it and why, and whether it has a security consequence. A keyword sentence in text that disclaims normativity, or that states common practice rather than a requirement, is triaged `practice` instead and counted apart from the obligations, as Practice explains; such a sentence is covered by a case that cites it as a clause or quotes it in an `INTEROP` assertion's basis. A sentence with no judgment is reported as unassessed rather than guessed. A judgment that no longer identifies exactly one sentence of its pinned text is refused (a sentence repeated in the text is identified by its section and, if needed, its occurrence within that section), so re-pinning a specification forces the triage to be revisited. The report measures which sentences are cited, not how well; that judgment belongs in a dated assessment that cites the report, written by hand beside it. The first is [`coverage/assessment-2026-10.md`](coverage/assessment-2026-10.md).

## Continuous integration

CI runs at three levels:

The first two levels exist. The third is not built yet.

1. **On every pull request, cheaply:** the runner's own tests, validation of every case against the case schema, and regeneration of every case and of the clause coverage report, each with a byte-for-byte comparison.
2. **On every pull request, more slowly:** each adapter is built against its pinned implementation and run against the suite, and its results are compared with a baseline committed for that adapter. A regression fails the pull request. An improvement asks for the baseline to be updated in the same pull request.
3. **Nightly, advisory:** each adapter is built against its implementation's latest development head and run, and the conformance reports are kept as artifacts. Accumulated, those records are the compatibility matrix; nobody maintains one by hand.

## Security

A case that a released implementation handles unsafely is, in effect, a public proof of concept against that implementation. "Unsafely" means handling a hostile input in a way with a security consequence — accepting what should be rejected, retaining what should be dropped, letting one input disturb the processing of others, or crashing or hanging — whatever the level of the assertion it fails. The consequence decides, not the grade: an inferred SHOULD can still describe a real attack. That includes keripy.

Such a case is embargoed. It is held outside the public tree, in a private repository that mirrors the public one and adds the embargoed cases, until the affected project has been told privately and has had up to 90 days to ship a fix, as [`SECURITY.md`](../SECURITY.md) describes. The embargo takes precedence over every other rule here, including the rule that a case keripy contradicts is published as disputed. While a case is embargoed, nothing derived from it is published either: not its scenario, not baseline changes it would cause, and not nightly results that include it. CI runs embargoed cases only in the private repository. Case ids are allocated in the private mirror, from the same sequence as every other case, so an embargoed case keeps its id when it is published; until then the public tree simply has a gap in its numbering. Gaps are normal and carry no meaning.

The runner executes adapter programs, and adapters execute implementation code. The runner treats an adapter's output as untrusted: it bounds the size of every response, validates its shape before reading it, and enforces a time limit on every request.

## Terms

- **Case.** A fixed input and a set of assertions about it, in one file under `cases/`. Its id is permanent.
- **Assertion.** One checkable claim about what an implementation must report for a case, with the clause it rests on and that clause's requirement level. Its outcome is pass, fail, or not-applicable when it is conditional and its condition does not hold.
- **Adapter.** A small standalone program that connects one implementation to the runner over the adapter protocol. Beyond translating requests, it owes two invariants — a fresh state for every request, and quiescence after every delivered message — and it must declare any behaviour it supplies itself rather than delegating to the implementation.
- **Profile.** A named set of cases that an implementation can claim to pass, such as "passes every active MUST assertion in profile P", stated together with its SHOULD results. A profile's status comes from the maturity of the specification text its assertions cite. A non-normative profile reports interoperability, with a named implementation or with a stated common practice, and is never a conformance claim; a run of one gets the verdict `interoperable`, `not-interoperable`, `incomplete` or `no-evidence` (see Practice).
- **Conformance report.** The machine-readable output of a run: suite version, profile, adapter and implementation identity, composed behaviours, and the outcome of every assertion.
- **Disputed.** The status of a case whose expected values an implementation's behaviour contradicts, where the clause appears to say otherwise. A disputed case is excluded from conformance results until the specification working group settles it. Conflicts inside the specification's own text do not make a case disputed; they are recorded in `spec_conflicts`.
- **Bundle.** The input of an ACDC case: every KEL, registry event, schema and ACDC in the presented ACDC's provenance DAG, together with the presented ACDC. It also fixes the evaluation point, because it holds only what has happened by then.
- **Seen.** Of a KERI message: accepted into the validator's copy of the KEL. The specification calls this first seen and makes it permanent.
- **Trunk.** The undisputed path through a KEL. A superseded event is seen and off the trunk.
- **Verdict.** Of an ACDC: `valid`, `invalid` or `incomplete`. Cases grade only valid against not valid; whether a not-valid ACDC is invalid or incomplete is informative.
- **Self-agreement.** A pass where keripy both produced the expected value and is the implementation under test. It shows only that keripy agrees with itself, and the conformance report marks it so.
- **Embargoed.** The status of a case that would disclose an unfixed security defect in a released implementation; it is held in a private mirror until the affected project has had a chance to ship a fix.
